# Authoring curriculum

There are two ways to add content. Use whichever suits the job.

## 1. Admin console (no code)

Sign in as a Content Editor, Administrator or Owner and open **Admin → Curriculum**.

1. Open a course. Each unit and chapter shows its outline; written lessons link to the studio.
2. On a planned lesson, choose **Write lesson**. This creates a draft linked to that outline entry.
3. In the **lesson studio**, add blocks (text, definition, formula, worked example, callout, interactive activity, image, references), set each block's mode (Learn, Experiment, Practice; a walkthrough option shows under Experiment), and watch the **Preview** tab.
4. Add questions in the **Practice** tab. Multiple choice, numeric (with absolute or relative tolerance and units) and short answer are supported; every question needs a worked solution.
5. **Save draft revision** (each save is a numbered revision you can load later), run **Check**, then **Publish**. Publishing a lesson in a planned course moves the course to "in development". Make sure its unit and chapter are published too.

## 2. Content files (bulk, reviewable in git)

- Outlines: `content/outlines/*.txt` (format documented at the top of each file). Honors courses can `extends` an on-level course and add lessons.
- Lessons: `content/lessons/<slug>.ts`, using the helpers in `content/lib.ts`. Link a lesson to an outline entry with `=> <slug>`.
- Formulas: `content/formulas.ts`.
- Run `npm run content:check` to validate, then `npm run content:build` to write the current batch migration (`TARGET` in `scripts/build-content.ts`).

**Important: batches.** Migrations listed in `FROZEN` at the top of `scripts/build-content.ts` are never rewritten. Each build writes only the statements those files don't already contain into `TARGET` (currently `0033_lessons_batch_28.sql`). Once `TARGET` has been applied to any shared database (staging or production), add it to `FROZEN` and name the next batch (`0034_…`); otherwise new content would be silently skipped there, because D1 never re-runs an applied migration.

If you edit a lesson that already shipped, the builder emits a guarded `UPDATE … WHERE id = … AND <column> = <shipped value>`, so the fix applies only if nobody has changed that row in the admin console since. Also run the KaTeX check before shipping: every `$…$` segment must render (inline math only; `$$…$$` is not supported).

## Diagrams (static figures)

Use `figure(src, alt, caption?)` from `content/lib.ts` for a picture that explains better than a simulation would (types of discontinuities, a labeled related-rates setup). Put the SVG in `public/figures/<name>.svg`. `content:check` rejects a figure whose file is missing or whose alt text is shorter than 20 characters; write alt text that describes what the picture shows. Figures display on a white panel, so draw them for a light background; they then work in dark mode too. The existing diagrams are generated by a script with exact curves; keep labels clear of the curves and check them at phone width.

## Phone-width worked examples

Prose inside `\text{…}` in a step now wraps on phones, but long pure-math steps still scroll sideways. `python3 scripts/wide-steps.py 40` lists likely offenders; split them into two steps.

## Adding a simulation

Add a component in `src/components/sims/`, register its id in `src/components/sims/registry.tsx` and `shared/activities.ts` (with any configurable parameters), and use `SimShell` so it gets controls, live readouts and the assumptions panel. Every simulation must compute its results and list its assumptions and limits.

## Lesson modes

Lessons show three modes: Learn, Experiment and Practice. Watch mode was removed in session 20. Blocks still stored with `mode: "watch"` (guided walkthroughs) are shown under Experiment, and new walkthroughs should use `experiment`.

## Mobile

- On screens narrower than 1024 px, a simulation's picture stays pinned at the top (up to 48% of the screen height) while its controls scroll underneath. Keep pictures roughly 480 × 200–300.
- On touch screens slider thumbs are 28 px. Draggable SVGs need `touch-none` so dragging doesn't scroll the page.
- Check new pages at 360 and 390 px: `scrollWidth` must equal the viewport width.

## Hints

Every practice question should have one or two hints that point toward the method without giving the answer. `python3 scripts/hints.py dump <course-slug>` lists that course's questions whose hint list is empty, with an id for each. Write `{ "<id>": ["hint", …] }` to a JSON file and run `python3 scripts/hints.py apply <file.json>`. Ids are character offsets, so dump again after applying before writing more hints for the same lessons. Editing hints on an already-shipped question produces a guarded `UPDATE practice_questions SET hints = …` in the next migration; no new lesson is created.

## Type checking

`npx tsc --noEmit -p .` does not check the app code. Use `npm run typecheck`, which `npm run build` also runs.
